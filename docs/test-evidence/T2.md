## 1. Executive Summary

This report delivers end-to-end integration evidence across the entire Laptop Productivity Monitoring SaaS pipeline per **Prompt T2** and **Specification §§ 6, 7, 8, 9, 10, 12**.

The integration test suite exercises the live system without mock layers between core abstractions:
```
[Agent Core: Journal & Spool]
              │
              ▼ HTTPS (Bearer Auth, Checksums, Signatures)
[Django REST Framework API]
              ├──► [MySQL Transactional Database] (Batches, Events, Audit, Policies)
              └──► [Object Storage] (Presigned PUTs, SHA-256 Checksums, WebP Thumbnails)
                             │
                             ▼ Celery Engine
              [Timeline Reconstruction & Daily Metrics Engine]

                             ▼
              [Reports & Dispute Analytics API]
```

All 9 end-to-end integration scenarios execute with direct database, storage, and journal assertions, confirming end-to-end correctness, idempotent retries, strict multi-tenant isolation, version enforcement, and long-term offline backlog replay.

## 3. Direct Multi-Layer Verification Evidence

### Scenario 1: Complete Happy-Path Pipeline Trace
1. **Enrollment**:
   - Enrollment token issued via `POST /api/devices/enrollment-tokens` with single-use limit and 24h expiration (`token_id: e4da0be1-...`).
   - Agent exchanges raw token via `POST /api/agent/enroll` -> Device `ACME-LAPTOP-01` created in MySQL, unique credential issued (`AgentCredential.create_secret_credential`).
2. **Policy & Heartbeat**:
   - Agent pulls effective policy (`screenshot_interval=60s`, `idle_threshold=300s`, `min_version="1.0.0"`).
   - Agent sends heartbeat (`POST /api/agent/heartbeat`) -> `device.last_seen_at` updated in database.
3. **Event Ingestion**:
   - Agent queues `app.active` and `session.idle_start` in local SQLite encrypted journal.
   - `sync_worker.sync_events()` sends batch to `POST /api/agent/events/batch`.
   - **Database Check**: `EventBatch` row committed (`status=ACCEPTED`, `accepted_count=3`), 3 `ActivityEvent` records inserted.
   - **Agent Check**: Local SQLite journal pending count drops from 3 to 0.
4. **Two-Phase Screenshot**:
   - Agent spools screenshot in local spool directory.
   - Phase 1: `POST /api/agent/screenshots/upload-intents` returns presigned upload URL and tenant-scoped non-guessable object key (`tenants/<tenant_id>/devices/<device_id>/...`).
   - Phase 2: Presigned upload puts JPEG bytes directly into object storage.
   - Phase 3: `POST /api/agent/screenshots/complete` validates SHA-256 checksum and PIL image integrity, saves WebP thumbnail derivative.
   - **Storage Check**: Object storage contains original bytes matching SHA-256 and thumbnail WebP.
   - **Agent Check**: Local spool file purged on confirmed server finalization.
5. **Timeline Analytics & Reports**:
   - `process_device_timeline_task(tenant_id, device_id)` reconstructs intervals deterministically.
   - `AppUsageInterval` and `DailyMetrics` records generated.
   - `GET /api/reports/daily?device_id=...` and `GET /api/reports/timeline?device_id=...` return aggregated active time and intervals.

### Scenario 2: Partial Batch Acceptance (E36)
- Sent batch with 1 valid `app.active` event and 1 unknown `unsupported.malicious.event`.
- Backend response: HTTP 207 Multi-Status, `batch.status = "partial"`, `accepted = [e1]`, `rejected = [e2]`.
- Database invariant: `ActivityEvent` table contains only `e1`.
- Agent invariant: `e1` deleted from SQLite journal; `e2` retained for inspection/retry.

### Scenario 3: Lost Response Idempotency (E02, E03, E31)
- Initial batch transmission succeeds on server and commits event `e1`. Response dropped before agent processes it.
- Agent resends identical batch with `e1.id` and original payload.
- Server detects `(tenant, id)` match with identical canonical JSON payload.
- Server returns HTTP 200 with `already_accepted: [e1.id]`.
- Database invariant: `ActivityEvent.objects.filter(id=e1.id).count() == 1` (zero duplicates).
- Agent invariant: Journal purged on receipt of `already_accepted`.

### Scenario 4: Revoked Device Upload Cessation (E24, E38)
- Admin issues `POST /api/devices/<device_id>/revoke`.
- Device status updated to `REVOKED` in MySQL.
- Agent attempts event batch upload -> `DeviceBearerAuthentication` returns HTTP 403 Forbidden ("Device access has been revoked").
- Agent `SyncWorker` marks `self.is_revoked = True` and enters stopped state (E38).
- Subsequent sync calls immediately short-circuit without attempting network requests.

### Scenario 5: Agent and Server Version Mismatch (E16)
- Policy updated to `min_agent_version="2.0.0"`.
- Agent running version `1.0.0` fetches policy and evaluates semver constraints.
- Invariant confirmed: `(1, 0, 0) < (2, 0, 0)`, triggering upgrade requirement.

### Scenario 6: Two-Phase Screenshot Validation and Idempotency (E51, E52, E53)
- Intent requested with valid SHA-256 checksum.
- Finalize called with incorrect checksum `"0" * 64` -> rejected with HTTP 400 (`CHECKSUM_MISMATCH`).
- Finalize called with matching SHA-256 checksum -> accepted with HTTP 200, status finalized.
- Idempotent retry: Repeat finalize call with same credentials -> returns HTTP 200 finalized, without creating duplicate rows.

### Scenario 7: Policy Change Propagation (E37, E70)
- Admin issues `PATCH /api/policies/<policy_id>` updating `screenshot_interval_seconds` from 60 to 120 and `idle_threshold_seconds` from 300 to 180 with `expected_version=1`.
- Backend increments policy version to 2.
- Agent fetches `/api/agent/policy`, receives updated values, and applies version 2.

### Scenario 8: Multi-Tenant Concurrent Isolation (E45, E46)
- Device A (Tenant A) sends batch authenticated with Tenant A bearer credentials but targeting Tenant B device identifier.
- Server rejects unauthorized spoofing; 0 events inserted for Tenant B.
- Tenant B records daily metrics. Tenant A admin queries `GET /api/reports/daily`.
- Response results set contains 0 items belonging to Tenant B; querying Tenant B device returns empty results.

### Scenario 9: 7-Day Offline Backlog Replay
- 70 historical events generated across 7 consecutive simulated days.
- Agent drains queue in bounded batches of 25 items (`max_batch_size=25`).
- Total batches: 3; total synced: 70; journal pending: 0.
- Timeline engine executes across the entire span:
  - Generates `DailyMetrics` across all 7 days with non-zero active seconds and valid `calc_version=1`.
  - Reports API queries across the 7-day range return exact day-by-day metrics.
